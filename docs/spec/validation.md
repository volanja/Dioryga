# アプリケーション層の検証規則

設計書は繰り返し「DB制約ではなくアプリケーション層で検証する」と述べているが、その規則は15以上の章に散在している。実装のために集約したもの。括弧内は該当章。

## なぜDB制約にしないか

1. **PostgreSQLとSQLiteで書き方が異なる、または片方に存在しない**（Row Level Security、トリガー等）。v1から両DB対応する方針と相容れない
2. **別テーブルの列同士の比較**や**条件付きの一意性**など、DB制約では表現しきれない
3. **多態的参照**（`item_type`/`item_id`）は外部キー制約を張れない

**例外**：`UNIQUE(subnet_id, ip_address) WHERE to_date IS NULL` の部分インデックスは両DBが対応するため、DB制約として実装してよい（14.2）。

## 検証の強さは3段階

| レベル | 扱い |
|---|---|
| **エラー** | 拒否する。データの整合性が壊れるもの |
| **警告** | 記録するが拒否しない。実機が仕様の想定外であることはありうるため、拒否すると事実を記録できなくなる |
| **情報** | 表示のみ |

**原則として警告を選ぶ**（設計書6.1、22.2）。台帳は事実を記録することが目的であり、理想的な構成を強制する場ではない。

## 1. 認可（RBAC）

認証と認可を**towerミドルウェアの2層**に分ける（20.10）。

```
① 認証：Cookie or Bearerトークン → User を解決
② 認可：User + 対象 → 許可/拒否
```

| # | 規則 | レベル | 出典 |
|---|---|---|---|
| A-1 | **System Adminガード**：`is_system_admin=true` のUserによる `/projects/**` へのアクセスを、ロールの強弱に無関係に拒否する。**ロール判定とは独立したガードとして実装する** | エラー | 3章, 20.10 |
| A-2 | プロジェクトロール判定は、ユーザーが同一プロジェクトで持つ**いずれかのロール**が要件を満たすかで判断する（複数ロール兼務を許すため） | エラー | 5章 |
| A-3 | 認証を要求しないのは `/login`・`/setup`・ヘルスチェック・**静的アセット**のみ。**それ以外は認証必須をデフォルトとする**（許可リスト方式）。静的アセットを含めるのは、ログイン画面自身がCSSを読むため | エラー | 20.10 |
| A-3b | `must_change_password` の間は、パスワード変更画面・ログアウト・**静的アセット**のみを通し、他はすべて変更画面へ誘導する。静的アセットを含める理由はA-3と同じ | エラー | 20.6, 20.10 |

| A-4 | カタログマスタの作成・編集は「いずれか1つ以上のプロジェクトでOperator以上」を要する。**System Adminはカタログを編集できない** | エラー | 18.1 |
| A-5 | 1プロジェクトにつきPrimary Administratorは最大1名、Secondaryも最大1名 | エラー | 5章 |
| A-7 | **語彙・型の整合性は緩めない。**送られてきた値が語彙外・解釈不能・存在しないIDの場合は、既定値へ倒さずエラーで拒否する。選択肢はサーバが描画しているため、そうした値が届くのは改竄かクライアントの不具合しかありえず、**黙って別の値を保存すると気付けない。**不変条件6（検証は警告に留める）は「実機が仕様の想定外でありうる」ことへの配慮であり、この規則とは別 | エラー | 8.6 |
